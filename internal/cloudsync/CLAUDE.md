# Cloud sync

Notes on rclone (`cloud`) and the sync engine (`syncer`). Paths in backticks are relative to the repository root.

- `cloud.Client` opens each remote once at its root (shared via rclone's `fs/cache`) and addresses files relative to it. Don't call `fs.NewFs` per operation or on deep/missing paths: on OneDrive that costs ~10s per call (measured). Folder creation (~4s each) and server-side copies (async, ~9s) are OneDrive's own costs. The cache is cleared when remotes change (`cache.Clear` in config.go). `tuneRemote` turns off Dropbox upload batching (~3-4s → ~1s per upload) unless the remote sets `batch_mode`.
- rclone config is global state: `cloud.Init` once per process; config state-machine calls go through `configMu`.
- The sync decision logic is `syncer.Decide`; back up the side being overwritten before push/pull when `BackupRetention > 0` (default 0 = off, since the zip upload slows syncs; also skipped when the transfer changes nothing). 0 is a valid persisted value — don't treat it as "unset". Backups are one zip each (`backups/<time>_<device>_<kind>.zip`, see `syncer/backup.go`): folder creation and server-side copies are slow on OneDrive. Older folder backups must stay listable/restorable/prunable. Names are timestamp-prefixed (ms precision) and must stay sortable.
- Save folders may have no file path: on Android a folder granted through the Storage Access Framework is `:saf:<authority>/<tree id>[/<sub>]`, reached through `internal/cloudsync/localfs` (an `FS` the app registers via `mobile.SetStorage`) and, for transfers, the hidden rclone backend `saf` (`cloud/saf.go`). In `syncer`, every read or write of a save folder goes through `localfs` (`Open`, `Remove`, `MkdirAll`, `Join`, `IsAbs`, `Walk`), never `os`/`filepath` directly; for plain paths those helpers are `os` exactly. `pathvar` leaves `:saf:` paths untouched.
- Push/pull transfer only the difference: `syncer.diff` compares the local scan and the cloud manifest by size + SHA-256, then `Client.Upload`/`Download` copy exactly those files and `Client.DeleteFiles` / `os.Remove` remove the rest. Don't go back to `rclone sync` for this (it compares by modtime/size and re-transfers or, on backends without modtimes, misses same-size changes). On push, manifest entries are checked against a listing of the cloud folder, so files left by an interrupted upload are repaired or removed. Cloud saves may be compressed (`Manifest.Format`, `syncer/compress.go`, "Compressed saves" in `docs/architecture.md`): in a format 1 folder every object under `current/` is `<name>.zst`, never a mix (that is what keeps older versions from writing compressed bytes or half a pull into a save folder); the manifest's keys, `size` and `sha256` stay those of the uncompressed file (`storedSize` is the object's); objects of a previous format are deleted only after the new manifest is written; backup zips always hold uncompressed files. `core.Engine` writes `FormatRaw` until a release has shipped that reads format 1.
