# Android

Notes for the Android app and the `mobile` bridge. Paths in backticks are relative to the repository root.

- Android (`docs/android-architecture.md`): `scripts/android-build.ps1` (Windows) / `scripts/android-build.sh` (Linux, macOS) build the Go core (gomobile bind of `mobile` into `android/app/libs/carryover-core.aar`; alone: `scripts/android-bind.sh`, rerun after Go changes) and the APKs into `dist/carryover-<version>-android-<abi>[-debug].apk`; `-Release`/`--release` signs with the key from `CARRYOVER_KEYSTORE`, `CARRYOVER_KEYSTORE_PASSWORD`, `CARRYOVER_KEY_ALIAS` (never commit a keystore), `-SkipBind`/`--skip-bind` reuses the Go core. Gradle reads version and ABIs from `-Pcarryover.versionName/versionCode/abis`. CI (`ci.yml`, job `android`) builds it and runs `testDebugUnitTest lintDebug` (lint errors fail it); `release.yml` attaches signed APKs, with the key from the `CARRYOVER_KEYSTORE_BASE64`/`_PASSWORD`/`CARRYOVER_KEY_ALIAS` secrets. `mobile` is the only API Kotlin sees: JSON strings in and out plus the `Host` callback interface; an Android process has no `HOME` or writable `/tmp`, so `mobile.Init` sets `HOME`/`TMPDIR`/`XDG_*` itself, and rclone's OAuth reaches the browser through `oauthutil.OpenURL` -> `Host.OpenURL`. `GOOS=android` also satisfies the `linux` build tag (`_other.go` files are compiled in). Android keeps its launch settings in the existing per-device fields, no catalog change: `EmulatorDevice.Exe` = `package` or `package/activity`, `EmulatorDevice.Args` = optional `am start`-style template with `{rom}` (parsed by `android/.../core/Launch.kt`), `EmulatorConfig.Rom` = path or `content://` URI, `DeviceConfig.Exe` = an Android game's package. Desktop code must keep reading only its own device's launch fields. Screens build on `ui/kit/Kit.kt` and the look in `ui/kit/Theme.kt`, the twin of the desktop's `ui/kit` (`AppButton`, `Callout`, `EmptyState`, `SectionCard`, `PageTopBar`, `PageColumn`; `StyleTest` fails on raw Material buttons/cards, literal radii and colours, filled icons). Motion ("Motion" in `docs/android-architecture.md`, `ui/kit/Motion.kt`): what is on its way out gets `Modifier.inert()` and draws from the state it was given, `ListRows` takes a key and stays composed while empty (in a `ListCard`), items of a list that uses `animateItem` have keys and those below a growing card use `placementSpec = PlacementMotion` (the pages' `SharedTransitionLayout` otherwise makes them jump ahead of it), and a game's cover is marked with `sharedCover` once per page. Android UI text goes in `res/values/strings.xml` with translations in `res/values-es/`, `res/values-in/` (Bahasa Indonesia) and `res/values-pt-rBR/` (`CatalogTest` checks every `values-*/strings.xml` against English and that `ui/`/`launch/` pass no literal to `Text(...)`); the theme is the core's `Settings.Theme`, the language per app (`AppLanguage`). The app shows only what plays on Android (`EmulatorPresets.onAndroid`, `GameView.forAndroid`): map a new desktop emulator preset with an Android app there. `launch/LaunchActivity` is exported (frontends, shortcuts; `docs/android-frontends.md`): it may only start apps set up on this device as an emulator or a game's app, never Carryover, and only passes on URI grants the caller gave (`launch/Forward.kt`, unit tested); keep those checks. `android/.../ui/` is split by folder: `kit` (building blocks, theme, focus, page insets), `nav` (`Screen`, `Nav`) and `state` (`AppViewModel`, `DisplayLogic`) import no other `ui` folder, `components` (shared widgets that know the app) only `kit` and `state`, and one folder per feature (`library`, `game`, `emulators`, `settings`, `cloud`, `backups`, `trash`, `art`; its screens with their view model) only those four and itself, never another feature; `ui/App.kt` is the shell that ties them together. The app's layers are checked by `LayeringTest`: `ui/` screens (not `*ViewModel.kt`) never use `Core`, `AppPrefs`, `AppServices`/`SettingsRepository`, `SessionManager`/`SessionService` or `BackgroundSync`; `core/` imports nothing above it, `data/` nothing from the screens; the session rules (`session/SessionManager`, `PlayFlow`, `PendingUploads`, `Front`) import no `android.*`, so they run in JVM tests against a fake `SessionCore`. View models are one per area (`AppViewModel`, `SettingsViewModel`, `CloudViewModel`, `TrashViewModel`, `ArtViewModel`, `BackupsViewModel`, `SuggestViewModel`, `LaunchViewModel`), plain `ViewModel`s with no `android.*` import (`LayeringTest`): they take `AppServices` (`data/`: the `SettingsRepository` shared state, `Messenger`/`Texts`, the `CoreApi`, the `AppPlatform` for everything Android) and `LaunchViewModel` a `LaunchPlatform` made for the incoming intent; tests pass the fakes in the test sources; syncing is `data/SyncController` (plain Kotlin over `SyncCore`); `Core` is the only real `CoreApi`: add a new bridge call to `core/CoreApi.kt`, and a word the core sends (action, kind, answer) as an enum in `Models.kt` with a default for unknown values.
