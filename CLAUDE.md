# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Carryover: Go desktop game launcher with a MyGo GUI (`ui/`, immediate mode, no cgo) that syncs saves through rclone, embedded as a Go library. See README.md and `docs/` for features and usage, `docs/architecture.md` for the package layers, the shared `services` API, the GUI structure and the cloud layout, and CONTRIBUTING.md for build, test and packaging steps.

## Commands

- The GUI is [MyGo](https://github.com/egoist/mygo) (Go 1.27.3): no cgo, no C compiler, no GUI dev packages; every build cross-compiles from any host, and `CGO_ENABLED=0 go test ./...` runs the whole suite. At run time Linux needs GTK 3 (loaded with dlopen). `mygo.json` (name, identifier, icon) configures `go tool mygo build`, which makes the Windows exe resources (icon, per-monitor DPI manifest, version info) and the macOS `.app`.
- Build app (Windows): `go build -trimpath -ldflags "-s -w -H windowsgui" -o dist/carryover.exe .` (all build output goes to `dist/`; `-s -w` strips debug info, ~37 MB instead of ~80 MB; drop it only when debugging. `-H windowsgui` hides the console, and `attachConsole` re-attaches it for CLI subcommands). Exe with icon, manifest and version info: `go tool mygo build -platform windows/amd64 -skip-installer` (writes `dist/mygo/windows-amd64/Carryover.exe`). Releases are built by `.github/workflows/release.yml` from `v*` tags. Windows release files (portable zip with `carryover.exe` + NSIS installer, `packaging/windows/`) come from `.\scripts\windows-package.ps1 [-Version x.y.z]`, locally and in CI; it sets `version` in `mygo.json` for the build and restores the file.
- Versions: the git tag is the only version. Release jobs run `scripts/stamp-version.sh <tag> <sha>`, which writes the git-ignored `internal/app/version/zz_release.go` setting `version.Version`/`Commit` (not `-ldflags -X`, so `go build` and `mygo build` pick it up the same way); other builds report "dev" plus the VCS commit.
- Build app (Linux / Steam Deck) from any host: `GOOS=linux GOARCH=amd64 go build -trimpath -ldflags "-s -w" -o dist/linux/carryover .` (no cgo, so no Docker or cross compiler). The AppImage and the container image come from the `Dockerfile` (`docker build --target appimage-out --output type=local,dest=dist .`).
- Build app (macOS): plain `go build -trimpath -ldflags "-s -w" -o dist/carryover .`. Release files (universal `Carryover.app` in a zip made with `ditto`, ad-hoc signed, not notarized) come from `scripts/macos-package.sh [x.y.z]`, locally and in CI; it runs `go tool mygo build -platform darwin/universal` and restores `mygo.json`. The program inside the bundle is `Carryover`; `isSelfShortcut` matches a name starting with "carryover", whatever its case.
- Android (`docs/android-architecture.md`): `scripts/android-build.ps1` (Windows) / `scripts/android-build.sh` (Linux, macOS) build the Go core (gomobile bind of `mobile` into `android/app/libs/carryover-core.aar`; alone: `scripts/android-bind.sh`, rerun after Go changes) and the APKs into `dist/carryover-<version>-android-<abi>[-debug].apk`; `-Release`/`--release` signs with the key from `CARRYOVER_KEYSTORE`, `CARRYOVER_KEYSTORE_PASSWORD`, `CARRYOVER_KEY_ALIAS` (never commit a keystore), `-SkipBind`/`--skip-bind` reuses the Go core. Gradle reads version and ABIs from `-Pcarryover.versionName/versionCode/abis`. CI (`ci.yml`, job `android`) builds it and runs `testDebugUnitTest lintDebug` (lint errors fail it); `release.yml` attaches signed APKs, with the key from the `CARRYOVER_KEYSTORE_BASE64`/`_PASSWORD`/`CARRYOVER_KEY_ALIAS` secrets. `mobile` is the only API Kotlin sees: JSON strings in and out plus the `Host` callback interface; an Android process has no `HOME` or writable `/tmp`, so `mobile.Init` sets `HOME`/`TMPDIR`/`XDG_*` itself, and rclone's OAuth reaches the browser through `oauthutil.OpenURL` -> `Host.OpenURL`. `GOOS=android` also satisfies the `linux` build tag (`_other.go` files are compiled in). Android keeps its launch settings in the existing per-device fields, no catalog change: `EmulatorDevice.Exe` = `package` or `package/activity`, `EmulatorDevice.Args` = optional `am start`-style template with `{rom}` (parsed by `android/.../core/Launch.kt`), `EmulatorConfig.Rom` = path or `content://` URI, `DeviceConfig.Exe` = an Android game's package. Desktop code must keep reading only its own device's launch fields. Screens build on `ui/kit/Kit.kt` and the look in `ui/kit/Theme.kt`, the twin of the desktop's `ui/kit` (`AppButton`, `Callout`, `EmptyState`, `SectionCard`, `PageTopBar`, `PageColumn`; `StyleTest` fails on raw Material buttons/cards, literal radii and colours, filled icons). Android UI text goes in `res/values/strings.xml` with Bahasa Indonesia in `res/values-in/` (`CatalogTest` checks every `values-*/strings.xml` against English and that `ui/`/`launch/` pass no literal to `Text(...)`); the theme is the core's `Settings.Theme`, the language per app (`AppLanguage`). The app shows only what plays on Android (`EmulatorPresets.onAndroid`, `GameView.forAndroid`): map a new desktop emulator preset with an Android app there. `launch/LaunchActivity` is exported (frontends, shortcuts; `docs/android-frontends.md`): it may only start apps set up on this device as an emulator or a game's app, never Carryover, and only passes on URI grants the caller gave (`launch/Forward.kt`, unit tested); keep those checks. `android/.../ui/` is split by folder: `kit` (building blocks, theme, focus, page insets), `nav` (`Screen`, `Nav`) and `state` (`AppViewModel`, `DisplayLogic`) import no other `ui` folder, `components` (shared widgets that know the app) only `kit` and `state`, and one folder per feature (`library`, `game`, `emulators`, `settings`, `cloud`, `backups`, `trash`, `art`; its screens with their view model) only those four and itself, never another feature; `ui/App.kt` is the shell that ties them together. The app's layers are checked by `LayeringTest`: `ui/` screens (not `*ViewModel.kt`) never use `Core`, `AppPrefs`, `AppServices`/`SettingsRepository`, `SessionManager`/`SessionService` or `BackgroundSync`; `core/` imports nothing above it, `data/` nothing from the screens; the session rules (`session/SessionManager`, `PlayFlow`, `PendingUploads`, `Front`) import no `android.*`, so they run in JVM tests against a fake `SessionCore`. View models are one per area (`AppViewModel`, `SettingsViewModel`, `CloudViewModel`, `TrashViewModel`, `ArtViewModel`, `BackupsViewModel`, `SuggestViewModel`, `LaunchViewModel`), plain `ViewModel`s with no `android.*` import (`LayeringTest`): they take `AppServices` (`data/`: the `SettingsRepository` shared state, `Messenger`/`Texts`, the `CoreApi`, the `AppPlatform` for everything Android) and `LaunchViewModel` a `LaunchPlatform` made for the incoming intent; tests pass the fakes in the test sources; syncing is `data/SyncController` (plain Kotlin over `SyncCore`); `Core` is the only real `CoreApi`: add a new bridge call to `core/CoreApi.kt`, and a word the core sends (action, kind, answer) as an enum in `Models.kt` with a default for unknown values.
- Ludusavi save-path index (`internal/saves/ludusavi/index.json.gz`, embedded) is generated: `go run ./internal/saves/ludusavi/gen` downloads the manifest and rebuilds it. Don't edit it by hand.
- Go: `golangci-lint run ./...` (config in `.golangci.yml`; `golangci-lint fmt ./...` fixes formatting/imports) and `go test ./...` (syncer tests use a temp-dir `local` remote — no network)

## Gotchas

- `services/` is the API over `internal/core` shared by both apps: the desktop GUI and Android (through `mobile`). Keep GUI-toolkit, Steam-only and Android-only assumptions out of it; pass a platform choice in as a parameter (`defaultRootOn(goos, ...)`) rather than adding `runtime.GOOS` checks. `mobile` may read `internal/core` directly, but every change goes through `services`, which holds the locks, session checks and `Bus` events (`TestMobileWritesThroughServices` allowlists its `s.core` reads). It reports changes through `services.Bus` (library/status/prompt/sync-progress callbacks, called on arbitrary goroutines). On the desktop `ui/store` is its only listener: it keeps the shared state and tells pages by topic (see "Desktop GUI" in `docs/architecture.md`); on Android `mobile` forwards them to `Host`.
- UI text goes through `ui/i18n` (its own go-i18n localizer, no toolkit import): write `i18n.L("English text")` (templates: `i18n.L("Hi {{.Name}}", map[string]any{...})`, counts: `i18n.N`) and add the same key to `ui/i18n/translations/en.json` (`TestTranslationCatalog`, which scans every Go file under `ui/`, fails otherwise); `i18n.N` keys need `one`/`other` forms there. Add a language by copying `en.json` to `<lang>.json` and listing it in `i18n.Options` (`ui/i18n/i18n.go`); `TestLanguageCatalogsMatchEnglish` checks keys and placeholders. The Language setting applies at startup (`i18n.Load` runs `i18n.Init` once per process). Never call `i18n.L` at package level (catalogs load in `start`); use functions, not maps/consts.
- Text the core shows to users (status, progress, errors people can act on, hints) is a message of `internal/app/msg`, never a plain string (see "Translating the core's text" in `docs/architecture.md`): define it in `catalog.go` (one line each; codes are stable, they are saved and read by the apps), make errors with `msg.X.Err/Wrap` instead of `errors.New`/`fmt.Errorf`, and give a view field with such text a `...Msg` field next to it (clear both together). Add it to every `ui/i18n/translations/*.json` (the English template is the key), both `strings.xml` files and `data/CoreMessages.kt` (`TestCoreMessagesAreInTheCatalog`, `TestAndroidCatalog`). Apps show it with `i18n.Msg/Text/Err` (desktop) or `Texts.core/error`, `coreText` (Android), never `err.Error()` or `e.message`. Every exported `mobile` function that returns an error starts with `defer wire(&err)`. Technical errors, the log and the CLI stay English.
- Layout: `internal/` is grouped by layer (`app`, `cloudsync`, `saves`, `stores` at the bottom; `library`, `launcher`, then `core` above them). Import only from your own group or below, never upward; put a new package in the group that matches what it knows about (see "Code map" in `docs/architecture.md`). `ui/kit` holds the reusable MyGo building blocks (cards, badges, rows, layouts, palette/theme, toaster, image cache, `kit.OnUI`/`kit.Async`); it must stay toolkit-only, with no `i18n`, `services` or `core` import and no user-visible text (pass labels in), so new generic widgets go there with exported names, and anything that knows about games or translations stays in the other `ui/` packages. Tests that run UI work inline set `kit.OnUI`. Paths of the generated files: `internal/app/version/zz_release.go`, `internal/saves/ludusavi/index.json.gz`.
- Threading: MyGo state is used on the UI goroutine only (the main one). Work that starts elsewhere (a goroutine, a `Bus` callback) hops back with `kit.OnUI`, which also asks every window for a new frame; use `kit.Async`/`kit.Async0` for service calls that do I/O so the UI never blocks. MyGo draws the window every frame from Go code (immediate mode): a page is `View(c *ui.Context)`, reads its ViewModel, and keeps `ui.Handle`s and scroll positions; two elements under one parent must not share a key (`c.Key(...)`): create each element once, even when its style depends on state.
- Controller/keyboard use: a gamepad works everywhere through one `kit.Navigator` per window (`ui/shell/gamepad.go` sets its hooks; `kit.MygoPad` reads the first pad through MyGo's gamepad package — XInput, evdev, GameController — only in Game Mode or when Steam started Carryover (`padWanted`): started by hand, Steam's Desktop Layout already turns the controller into mouse and keys, and reading it too doubles every press). MyGo cannot list a window's focusable controls or click one from code, so every control the D-pad should reach is registered while building it: `nav.Item(handle, element, action)` (`nav.Handle(key)` keeps handles for controls drawn in loops); the D-pad picks the next control by the boxes of the last frame (`kit/spatialpick.go`), A runs the item's action (the first A with nothing focused only picks a start), B runs the open dialog's back or the page's, LB/RB switch sections, X searches, Y syncs, View toggles full screen, the right stick scrolls the page's `Scroll()`. Dialogs are `kit.Dialog`s on `env.Dialogs()` (or `kit.Confirm`), each a scope of the Navigator that starts on its `kit.FocusSafe` control; a native `Select` or text field can't be opened with A, so use `kit.SelectOf` (a drawn field with a `ui.PopoverBase` list below it, one look for mouse, keys and pad: the list is a Navigator overlay that starts on the current choice, A picks, B closes; a list the mouse opens, a `kit.MenuButton`'s too, starts with nothing focused, so only the row under the pointer is lit) and `kit.TextField` (A opens Steam's keyboard). MyGo rings only keyboard focus, so the Navigator draws the pad's ring itself (a spread shadow). Never make the default-focused button one that overwrites saves (`kit.FocusSafe`).
- MyGo pitfalls seen here: an element's `Click` in `ui.Tester` fails when it is outside the window (make the test window tall: `h.Tester.SetSize(w, h)`) and finds text by what it shows, not by an input's value (focus a field through `nav.Handle(key).Focus()` and `Type`); `Handle.Bounds` is of the committed frame, so the Navigator acts on the previous frame's layout.
- The main GUI is single-instance per data dir (`internal/app/singleinstance`, loopback TCP + `state/gui.addr`); `carryover run` wrapper windows skip it.
- Only Google Drive, Dropbox, OneDrive, WebDAV, SFTP and SMB are supported (plus `local`, compiled in but hidden — needed to read save folders). Backend imports and the `Supported` list live together in `internal/cloudsync/cloud/backends.go`; keep them in sync (`TestProvidersMatchSupported`). Never import `backend/all`.
- Steam's "Exit game"/"Stop" kills the `carryover run` wrapper with the game (SIGKILL on Linux; on Windows a WM_CLOSE first, which the wrapper window ignores once the game has started, then a kill; on macOS a quit request, which reaches the window's close handler, then a signal to every process it started). MyGo quits the app on SIGINT/SIGTERM, so the wrapper window takes those signals over once the game runs (`wrapperClose.holdSignals`). `Play` writes the session marker (`state/<CloudKey>.session`, JSON with game + emulator) and calls `Core.WatchSession`, which starts `carryover finish-session --home <dir> <key>` through `internal/app/detach`: `systemd-run --user` on Linux, WMI `Win32_Process.Create` on Windows, a shell that backgrounds it and exits on macOS (launchd adopts it, so it is no longer a descendant Steam signals). Anything started directly by the wrapper dies with it, even outside the job object. Start it from `core.SelfExecutable()`, not `os.Executable()`: the AppImage's FUSE mount disappears with the wrapper, and the watcher then dies with SIGBUS. The watcher inherits no environment, so pass everything as arguments. Once the wrapper's local lock is free and the marker is still there, `Core.FinishSession` uploads (push only, never pull; a conflict is flagged), releases the cloud lock and returns a `core.Notice`, shown as a desktop notification (`internal/app/notify`). In gamescope, or if sending fails, the notice is saved to `state/notices/` and the UI shows it once (`TakeNotices`). Tests replace `startDetached`/`notifySend` in `main` and never set `Core.WatchSession` in `core`.
- Detached sessions (Android, `docs/android-architecture.md`): `Play` is `beginPlay` + `launcher.Run` + `playSession.end`; `Core.StartSession` runs only the start (no launch), writes the marker with `Detached` and releases the local lock, and `Core.EndSession` (= `FinishSession`) ends it. Nothing holds the local lock in between, so an open detached session (`Core.SessionOpen`) is what keeps manual sync/backup/restore (`core.ErrPlaying`, wraps `syncer.ErrLocked`) and `RecoverSessions` away; keep that check in any new operation that writes a game's local saves (`SyncService.lockGame`). Any failure of `EndSession` marks the marker `Ended` (the game has closed all the same), which makes the session no longer open; `Core.PendingSessions` lists those and `Core.EndPending` finishes only a marker still `Ended` (checked under the local lock), so a background retry (`SyncWorker`) can never end a session that was started again.
- Offline: play sessions, `FinishSession`, `RecoverSessions` and `SyncService.Sync`/`SyncAll` first call `Core.Online` (`cloud.Client.Probe`, bounded by `probeTimeout`; tests stub `Core.probe`), since rclone's retries take minutes without a network. Offline (`cloud.IsOffline`, wrapping `ErrOffline`) is not a sync error: no `SetError`, no failure prompt; the game starts without syncing, and after playing the marker is kept with `Ended` for `RecoverSessions`. Only a failed *plan* counts as offline before playing; a failed download keeps the prompt (the saves may be half replaced). Never hold a game's local lock across unbounded cloud I/O: `Play` waits only `localLockWait` for it.
- Syncs are cancellable through their `context` (`SyncService.Cancel`, `SessionService.Cancel` via `SessionUI.SyncCancelable`, Ctrl+C in `carryover sync`). Cancelling is not an error (no `SetError`), a partly written backup is deleted (`discardBackup`), and in a play session only the sync phases are cancellable — never the game process.
- `cloud.Client` opens each remote once at its root (shared via rclone's `fs/cache`) and addresses files relative to it. Don't call `fs.NewFs` per operation or on deep/missing paths: on OneDrive that costs ~10s per call (measured). Folder creation (~4s each) and server-side copies (async, ~9s) are OneDrive's own costs. The cache is cleared when remotes change (`cache.Clear` in config.go). `tuneRemote` turns off Dropbox upload batching (~3-4s → ~1s per upload) unless the remote sets `batch_mode`.
- rclone config is global state: `cloud.Init` once per process; config state-machine calls go through `configMu`.
- Self-update (`internal/app/update`, `services.UpdateService`): the release file names, their inner layout and `SHA256SUMS.txt` from `release.yml` are what installed versions download, so renaming or reshaping one breaks updating for everyone. A download without a matching checksum is never installed. The program is replaced under its own name (Steam shortcuts), files an update leaves behind use the `.update-new`/`.update-old` suffixes (`update.Cleanup` removes only those), `Install` is refused while `core.InUse`, and dev builds never check. Channels are the settings' `UpdateChannel` (`""` stable, `"prerelease"`); a channel never downgrades. The Windows installer is run as `/S /UPDATE` (no `/D`: it needs to be unquoted), and the desktop shell must close the single instance before starting the new version.
- Use `CARRYOVER_HOME=<dir>` to run the binary against an isolated data dir (settings, library, rclone.conf, state). Never test against the real user config dir.
- Emulators: a game's saves are keyed by a sync key, `core.SyncKey(gameID, emulatorID)` (`gameID` for the native profile, `gameID.emulatorID` for an emulator), which is what `syncer.Job.GameID` holds, so each emulator has its own cloud folder, state, lock, backups and session marker. `services/` methods that take a "gameID" for sync, backups, status and Steam accept either (`core.ParseKey`). Emulators (`library.Emulator`) are global; `DeviceConfig.Emulators`/`LastEmulator` and `Game.Emulators` hold the per-game data. Native games keep the bare id, so existing cloud data needs no migration; An emulator may opt in to another's cloud save (`GameEmulator.ShareWith`): `core.CloudKey` (cloud folder, cloud lock, local lock, session marker, backups) differs from `SyncKey` (sync state, `Job.StateKey`), so use the right one. `library.CatalogVersion` makes older clients refuse to rewrite a catalog they don't understand: 3 (written only once a device is forgotten, `Device.ForgottenAt` in `Catalog.Devices`; otherwise 2). A device's entries can't be deleted from the maps by hand (merges bring them back): use `Store.ForgetDevice`/`MoveDevice` (`Core.ForgetDevice`/`ReuseDevice`, which moves an earlier install's settings to this device's own ID, never the other way). Android's device ID is derived on a first start from `ANDROID_ID` (`mobile.Init`'s `deviceKey`, `appdir.DeviceIDFrom`), so keep it stable: never re-randomize it. A game's or emulator's own `UpdatedAt` decides whose shared fields win a merge: only stamp it when a shared field changes (`sameSharedGame`), never for a device-only edit. A sharing emulator's slots are filled in on load and not stored (`withSharedSlots`/`compactGame`). `Emulator.Platforms` (a shared field; empty: any) says where an emulator has a version: on another platform it is `NoVersionHere` in `services` views, left out of the desktop's ways to play and of the game's readiness (`Emulator.RunsOn` also treats a stored "Lemon" as Android only). `EmulatorService.Save` keeps the stored platforms when the input's are nil, so clients that don't know them never drop them.
- Emulator save suggestions (`internal/saves/emumanifest`, `services/emulator_suggest.go`) use the per-game manifests of sharkusmanch/ludusavi-emulator-manifests. They are downloaded on demand into `<data>/manifests/` and never embedded (tens of MB, and the repo has no license). `Emulator.Preset` + `EmulatorDevice.DataDir` say where `<root>` is; For yuzu-family emulators (Eden, Citron, Suyu, yuzu) a game's save is synced as the exact title folder of this device's own profile (`internal/saves/yuzu` reads the emulator's `profiles.dat`), as two slots keyed `account` and `device`: the profile ID differs per installation and must never be part of the cloud layout (it causes an "orphaned profile" on the other device). Ryujinx's manifest has one entry for all saves, so per-game Ryujinx saves come from its own index (internal/saves/ryujinx, the {ryujinx:<title id>:account|device} path token) and sync the committed copy (.../<id>/0) only.
- Launcher modes: `LaunchHeroic`, `LaunchLutris` and `LaunchBottles` start the game through that launcher (`heroicSpec`/`lutrisSpec`/`bottlesSpec` in `core/session.go`) so it keeps the launcher's Wine prefix; `Exe` only identifies the game and names the process to wait for, and `throughLauncher` keeps the mode on a direct Steam shortcut. Lutris is Linux only and read from its `games/<slug>-<ts>.yml` (never `pga.db`): `internal/stores/lutris` takes the library slug for `lutris:rungame/<slug>` from the file name, or from `game_slug` while the file still carries the installer's `slug` (saving a game's settings in Lutris renames the file). Bottles (Linux) is read from its config files only (`internal/stores/bottles`: `data.yml`'s `custom_bottles_path`, `bottle.yml`, `placeholder.yml`; `wineprefix` uses it too): `bottles-cli run -b <bottle Name>` with `-p <program>` only when that name is unique in the bottle, else `-e <exe>`.
- Deleting is a tombstone (`Deleted`, `DeletedAt`) that keeps the whole record for `library.TrashRetention` (30 days) so `Store.Restore` can undo it; `Store.ExpireTrash` (run from `Core.syncLibrary` and `LibraryService.Trash`) then reduces it to id/name/timestamps, as does `DeleteForever` (`gone()`), and `MergeGame`/`MergeEmulator` never merge settings back into a `gone` winner. Cover images are only removed at that point (`Core.DropImages`), never on a soft delete. "Delete with saves" (`LibraryService.DeleteWithSaves`, `EmulatorService.DeleteWithSaves`) purges the `games/<key>` cloud folders (`Core.SaveKeysOf*`/`PurgeSaves`, which list the cloud folder so stale emulator folders are found) before the tombstone is stripped. `Core.Leftovers` lists `games/` folders no game uses (not those of a game in the trash); `RestoreLeftover` rebuilds the game from the cloud manifest's slots.
- Games are identified by UUID, not name. Per-device data lives in `Game.Devices[deviceID]`; merges are per-device by `UpdatedAt`. `library.Store` returns deep copies — keep it that way.
- The sync decision logic is `syncer.Decide`; back up the side being overwritten before push/pull when `BackupRetention > 0` (default 0 = off, since the zip upload slows syncs; also skipped when the transfer changes nothing). 0 is a valid persisted value — don't treat it as "unset". Backups are one zip each (`backups/<time>_<device>_<kind>.zip`, see `syncer/backup.go`): folder creation and server-side copies are slow on OneDrive. Older folder backups must stay listable/restorable/prunable. Names are timestamp-prefixed (ms precision) and must stay sortable.
- Save folders may have no file path: on Android a folder granted through the Storage Access Framework is `:saf:<authority>/<tree id>[/<sub>]`, reached through `internal/cloudsync/localfs` (an `FS` the app registers via `mobile.SetStorage`) and, for transfers, the hidden rclone backend `saf` (`cloud/saf.go`). In `syncer`, every read or write of a save folder goes through `localfs` (`Open`, `Remove`, `MkdirAll`, `Join`, `IsAbs`, `Walk`), never `os`/`filepath` directly; for plain paths those helpers are `os` exactly. `pathvar` leaves `:saf:` paths untouched.
- Push/pull transfer only the difference: `syncer.diff` compares the local scan and the cloud manifest by size + SHA-256, then `Client.Upload`/`Download` copy exactly those files and `Client.DeleteFiles` / `os.Remove` remove the rest. Don't go back to `rclone sync` for this (it compares by modtime/size and re-transfers or, on backends without modtimes, misses same-size changes). On push, manifest entries are checked against a listing of the cloud folder, so files left by an interrupted upload are repaired or removed. Cloud saves may be compressed (`Manifest.Format`, `syncer/compress.go`, "Compressed saves" in `docs/architecture.md`): in a format 1 folder every object under `current/` is `<name>.zst`, never a mix (that is what keeps older versions from writing compressed bytes or half a pull into a save folder); the manifest's keys, `size` and `sha256` stay those of the uncompressed file (`storedSize` is the object's); objects of a previous format are deleted only after the new manifest is written; backup zips always hold uncompressed files. `core.Engine` writes `FormatRaw` until a release has shipped that reads format 1.
- `shortcuts.vdf` is binary VDF; writes must keep the `.carryover.bak` backup. Steam overwrites it on exit, so users must restart Steam.

## UI architecture

Look: pages share one look from `ui/kit` (see "Look and feel" in `docs/architecture.md`). Draw buttons with `kit.Btn`/`kit.IconBtn` (they register with the Navigator; a page's `DefaultFocus` finds one with `kit.BtnHandle(nav, key)`; `kit.BtnLarge()` for the page's main action), text inputs with `kit.Field`/`kit.TextArea`/`kit.SearchField`, switches with `kit.Toggle` (settings: `kit.ToggleRow`), content in `kit.Page`, rows with `kit.ListRow`, dialog buttons in `kit.Footer`, sizes from the `kit.Text*`/`kit.S*`/`kit.Radius*` tokens and icons from `kit.Icon*`. Warnings and errors go in `kit.Callout`, empty pages and lists show `kit.EmptyState`, long explanations fold into `components.Help`, secondary actions go in a "⋯" `kit.MenuButton`, which drops them down as a menu. Never `ui.Button`, `ui.PrimaryButton`, `ui.Checkbox`, `ui.TextInput`, `ui.TextArea`, a literal `FontSize` or a glyph such as ＋ or 🗑 in a page (`TestPagesUseTheKitStyle`). Split a long page view by topic into files of its package (as `pages/game` and `pages/editor` do).

`ui/` is split by role; read "Desktop GUI" in `docs/architecture.md` before adding a page. In short: a page is a ViewModel (state and rules, no widgets, tested without the toolkit) plus a view (`View(c *ui.Context)`), and it only sees the app through `env.Env` (its backend holds only `envcore.Services`). The page in `ui/pages/library` is the reference. Import order: `kit`, `i18n`, `textutil` <- `store` <- `envcore` <- `env` <- `components` <- `flows`, `prompts` <- `pages/*` <- `shell` <- `ui` (root, the composition root). `components` holds widgets and dialogs that know the app, `flows` the multi-step actions built on them (add a game, Steam import, SteamGridDB key, open in Steam). Under `ui/` only `shell` and the root import `internal/core`; everything else reaches `internal/` through `services` (`services/aliases.go` re-exports the types it needs). Pages never import `shell` or each other; they move with `env.Navigate`. `depguard` in `.golangci.yml` enforces this and keeps a `viewmodel.go` free of `github.com/egoist/mygo` and `i18n`; a ViewModel never holds translated text (the view calls `i18n.L`). ViewModels, backends, `store`, `envcore`, `i18n` and `textutil` must not reach any GUI toolkit, even transitively (`TestToolkitFree` in `ui/envcore`, depguard `toolkit-free`): put plain helpers in `ui/textutil`, not `kit`/`components`. Page contracts (`env.Page`, `Stateful`, `Guarded`, ...) have exported methods because the shell calls them from another package. Page tests use `ui/internal/uitest`, which never imports pages: a page's own view tests live in its package (an external `_test` package, with a shell that shows only that page and a stand-in for every other route), and the root `ui` package keeps only the whole-app tests, those that need several real pages at once (navigation history, the sidebar, gamepad reach, sync across pages).

## Platforms

Changes must work on Windows, Linux (Steam Deck/SteamOS, Proton via `-- %command%` wrapping) and macOS (no Proton; Steam wraps native games the same way). OS-specific code goes in `_windows.go` / `_darwin.go` / `_other.go` files with build tags; where a `_darwin.go` exists, `_other.go` is `!windows && !darwin` (Linux only), otherwise macOS gets the `_other.go` code. A game or emulator exe may be a macOS `.app` bundle (a folder): `launcher.BundleExe` resolves it to `Contents/MacOS/<CFBundleExecutable>` when starting, and the game/emulator exe pickers use `kit.PickProgram` (MyGo's system open dialog, which lets a bundle be chosen as one file); a program picked inside a bundle is still stored as the bundle (`launcher.AppBundle`). On macOS `{appdata}`, `{localappdata}` and `{xdgdata}` are all `~/Library/Application Support`; `Contract` prefers `{appdata}` there. The GUI needs no cgo, so `GOOS=linux CGO_ENABLED=0 golangci-lint run ./...` type-checks everything from any host.
