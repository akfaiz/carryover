# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Carryover: Go desktop game launcher with a Fyne GUI (`ui/`) that syncs saves through rclone, embedded as a Go library. See README.md for features and the cloud layout, and CONTRIBUTING.md for build and packaging steps.

## Commands

- Fyne needs cgo: `CGO_ENABLED=1` and a C compiler. On Windows use MSYS2 MinGW (`C:\msys64\ucrt64\bin` on `PATH`; install with `pacman -S mingw-w64-ucrt-x86_64-gcc`).
- Build app (Windows): `go build -trimpath -ldflags "-s -w -H windowsgui" -o bin/carryover.exe .` (`-s -w` strips debug info, giving ~46 MB instead of ~84 MB; drop it only when debugging. `-H windowsgui` hides the console, and `attachConsole` re-attaches it for CLI subcommands). Exe with icon: `go tool fyne package --os windows --release --name carryover` (writes `./carryover.exe` and bumps `Build` in `FyneApp.toml` — never commit that bump; `git checkout FyneApp.toml`). Releases are built by `.github/workflows/release.yml` from `v*` tags.
- Versions: the git tag is the only version. Release jobs run `scripts/stamp-version.sh <tag> <sha>`, which writes the git-ignored `internal/app/version/zz_release.go` setting `version.Version`/`Commit` (not `-ldflags -X`: `fyne package` drops GOFLAGS ldflags on its Windows rebuild); other builds report "dev" plus the VCS commit. Don't read the version from Fyne's `App.Metadata()` or `FyneApp.toml` — plain `go build` (Linux/AppImage) has no Fyne metadata.
- Build app (Linux / Steam Deck) from any host: `go run github.com/fyne-io/fyne-cross@latest linux -arch=amd64 -app-id com.akfaiz.carryover -name carryover` (needs Docker) and writes `fyne-cross/bin/linux-amd64/carryover`. On Linux itself plain `go build` works once the GL/X11 dev packages are installed.
- Ludusavi save-path index (`internal/saves/ludusavi/index.json.gz`, embedded) is generated: `go run ./internal/saves/ludusavi/gen` downloads the manifest and rebuilds it. Don't edit it by hand.
- Go: `golangci-lint run ./...` (config in `.golangci.yml`; `golangci-lint fmt ./...` fixes formatting/imports) and `go test ./...` (syncer tests use a temp-dir `local` remote — no network)

## Gotchas

- `services/` is the GUI's API over `internal/core`; it reports changes through `services.Bus` (library/status/prompt/sync-progress callbacks, called on arbitrary goroutines). `ui/` subscribes in `newUI`.
- UI text goes through Fyne's `lang` package: write `lang.L("English text")` (templates: `lang.L("Hi {{.Name}}", map[string]any{...})`, counts: `lang.N`) and add the same key to `ui/translations/en.json` (`TestTranslationCatalog` fails otherwise); `lang.N` keys need `one`/`other` forms there. Add a language by copying `en.json` to `<lang>.json` and listing it in `languageOptions` (`ui/i18n.go`); `TestLanguageCatalogsMatchEnglish` checks keys and placeholders. The Language setting applies at startup: Fyne cannot force a locale, so a chosen catalog is registered under the base `en` tag (`initTranslations`). Never call `lang.L` at package level (catalogs load in `start`); use functions, not maps/consts. `services/` messages are still English-only.
- Layout: `internal/` is grouped by layer (`app`, `cloudsync`, `saves`, `stores` at the bottom; `library`, `launcher`, then `core` above them). Import only from your own group or below, never upward; put a new package in the group that matches what it knows about (see CONTRIBUTING.md "Code map"). `internal/ui/kit` holds the reusable Fyne widgets (cards, badges, rows, layouts, palette/theme, toaster, image cache, `kit.OnUI`/`kit.Async`); it must stay pure Fyne, with no `lang`, `services` or `core` import and no user-visible text (pass labels in), so new generic widgets go there with exported names, and anything that knows about games or translations stays in `ui/`. Tests that run UI work inline set `kit.OnUI`. Paths of the generated files moved with it: `internal/app/version/zz_release.go`, `internal/saves/ludusavi/index.json.gz`.
- Fyne threading: widgets may only be touched on the UI goroutine. Wrap anything that runs from a goroutine or a `Bus` callback in `fyne.Do`; use the `async`/`async0` helpers in `ui/app.go` for service calls that do I/O so the UI never blocks.
- Fyne pitfalls seen here: a struct that only embeds `fyne.CanvasObject` is not drawn — make it a widget (`ExtendBaseWidget` + `CreateRenderer`, see `pathInput`); `widget.Label.SizeName` must be a `theme.SizeName*` constant (a wrong name gives text size 0 and panics in wrap-break); wrapping labels inside an HBox collapse — use `small()` or a Border layout.
- The main GUI is single-instance per data dir (`internal/app/singleinstance`, loopback TCP + `state/gui.addr`); `carryover run` wrapper windows skip it.
- Only Google Drive, Dropbox, OneDrive, WebDAV, SFTP and SMB are supported (plus `local`, compiled in but hidden — needed to read save folders). Backend imports and the `Supported` list live together in `internal/cloudsync/cloud/backends.go`; keep them in sync (`TestProvidersMatchSupported`). Never import `backend/all`.
- Syncs are cancellable through their `context` (`SyncService.Cancel`, `SessionService.Cancel` via `SessionUI.SyncCancelable`, Ctrl+C in `carryover sync`). Cancelling is not an error (no `SetError`), a partly written backup is deleted (`discardBackup`), and in a play session only the sync phases are cancellable — never the game process.
- `cloud.Client` opens each remote once at its root (shared via rclone's `fs/cache`) and addresses files relative to it. Don't call `fs.NewFs` per operation or on deep/missing paths: on OneDrive that costs ~10s per call (measured). Folder creation (~4s each) and server-side copies (async, ~9s) are OneDrive's own costs. The cache is cleared when remotes change (`cache.Clear` in config.go). `tuneRemote` turns off Dropbox upload batching (~3-4s → ~1s per upload) unless the remote sets `batch_mode`.
- rclone config is global state: `cloud.Init` once per process; config state-machine calls go through `configMu`.
- Use `CARRYOVER_HOME=<dir>` to run the binary against an isolated data dir (settings, library, rclone.conf, state). Never test against the real user config dir.
- Emulators: a game's saves are keyed by a sync key, `core.SyncKey(gameID, emulatorID)` (`gameID` for the native profile, `gameID.emulatorID` for an emulator), which is what `syncer.Job.GameID` holds, so each emulator has its own cloud folder, state, lock, backups and session marker. `services/` methods that take a "gameID" for sync, backups, status and Steam accept either (`core.ParseKey`). Emulators (`library.Emulator`) are global; `DeviceConfig.Emulators`/`LastEmulator` and `Game.Emulators` hold the per-game data. Native games keep the bare id, so existing cloud data needs no migration; An emulator may opt in to another's cloud save (`GameEmulator.ShareWith`): `core.CloudKey` (cloud folder, cloud lock, local lock, session marker, backups) differs from `SyncKey` (sync state, `Job.StateKey`), so use the right one. `library.CatalogVersion` 2 makes older clients refuse to rewrite a catalog they don't understand.
- Emulator save suggestions (`internal/saves/emumanifest`, `services/emulator_suggest.go`) use the per-game manifests of sharkusmanch/ludusavi-emulator-manifests. They are downloaded on demand into `<data>/manifests/` and never embedded (tens of MB, and the repo has no license). `Emulator.Preset` + `EmulatorDevice.DataDir` say where `<root>` is; For yuzu-family emulators (Eden, Citron, Suyu, yuzu) a game's save is synced as the exact title folder of this device's own profile (`internal/saves/yuzu` reads the emulator's `profiles.dat`), as two slots keyed `account` and `device`: the profile ID differs per installation and must never be part of the cloud layout (it causes an "orphaned profile" on the other device). Ryujinx's manifest has one entry for all saves, so per-game Ryujinx saves come from its own index (internal/saves/ryujinx, the {ryujinx:<title id>:account|device} path token) and sync the committed copy (.../<id>/0) only.
- Deleting is a tombstone (`Deleted`, `DeletedAt`) that keeps the whole record for `library.TrashRetention` (30 days) so `Store.Restore` can undo it; `Store.ExpireTrash` (run from `Core.syncLibrary` and `LibraryService.Trash`) then reduces it to id/name/timestamps, as does `DeleteForever` (`gone()`), and `MergeGame`/`MergeEmulator` never merge settings back into a `gone` winner. Cover images are only removed at that point (`Core.DropImages`), never on a soft delete. "Delete with saves" (`LibraryService.DeleteWithSaves`, `EmulatorService.DeleteWithSaves`) purges the `games/<key>` cloud folders (`Core.SaveKeysOf*`/`PurgeSaves`, which list the cloud folder so stale emulator folders are found) before the tombstone is stripped. `Core.Leftovers` lists `games/` folders no game uses (not those of a game in the trash); `RestoreLeftover` rebuilds the game from the cloud manifest's slots.
- Games are identified by UUID, not name. Per-device data lives in `Game.Devices[deviceID]`; merges are per-device by `UpdatedAt`. `library.Store` returns deep copies — keep it that way.
- The sync decision logic is `syncer.Decide`; back up the side being overwritten before push/pull when `BackupRetention > 0` (default 0 = off, since the zip upload slows syncs; also skipped when the transfer changes nothing). 0 is a valid persisted value — don't treat it as "unset". Backups are one zip each (`backups/<time>_<device>_<kind>.zip`, see `syncer/backup.go`): folder creation and server-side copies are slow on OneDrive. Older folder backups must stay listable/restorable/prunable. Names are timestamp-prefixed (ms precision) and must stay sortable.
- Push/pull transfer only the difference: `syncer.diff` compares the local scan and the cloud manifest by size + SHA-256, then `Client.Upload`/`Download` copy exactly those files and `Client.DeleteFiles` / `os.Remove` remove the rest. Don't go back to `rclone sync` for this (it compares by modtime/size and re-transfers or, on backends without modtimes, misses same-size changes). On push, manifest entries are checked against a listing of the cloud folder, so files left by an interrupted upload are repaired or removed.
- `shortcuts.vdf` is binary VDF; writes must keep the `.carryover.bak` backup. Steam overwrites it on exit, so users must restart Steam.

## Platforms

Changes must work on Windows and Linux (Steam Deck/SteamOS, Proton via `-- %command%` wrapping). OS-specific code goes in `_windows.go` / `_other.go` files with build tags. Fyne's GLFW driver needs cgo, so `GOOS=linux` type-checking from Windows doesn't work for `ui/` and `main`; check the other packages with `GOOS=linux CGO_ENABLED=0 golangci-lint run ./internal/... ./services/...` and verify the GUI with the fyne-cross build.
